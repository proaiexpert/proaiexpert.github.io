# 1. Portfolio doctrine

## 1.1 Главная идея

ProAI Expert portfolio — это не галерея красивых страниц. Это система доказательств того, что студия умеет:

- понять бизнес и его ограничения;
- сформировать стратегию;
- создать индивидуальную визуальную среду;
- построить content, intake and operational architecture;
- внедрить production-ready решение;
- честно показать status, evidence and boundaries.

Премиальность возникает из:

`точность + иерархия + воздух + доказательства + сдержанное движение + отсутствие фальши`

Она не возникает из:

`больше blur + больше parallax + больше glow + больше карточек + больше обещаний`

## 1.2 Shared shell / distinct project world

Все portfolio routes разделяют:

- exact current canonical header;
- rotating cube;
- language behavior;
- mobile menu;
- shell spacing and content geometry;
- canonical footer;
- focus behavior;
- shell reduced-motion behavior;
- common standards for typography quality, accessibility and performance.

Каждый case получает собственную внутреннюю среду:

- **Financial Stream:** structured, dark, systemic, evidence-led.
- **Alina Horb:** light editorial, portrait-led, human-scale.
- **Local Repair Pro:** tactile local-service, result-led, Pacific Northwest character.
- **ProAI Expert studio:** studio-system, process-led, restrained technological identity.

Общность должна ощущаться в качестве системы, а не в одинаковой палитре или одинаковых layouts.

## 1.3 Reference quality target

Каждая новая страница должна отвечать на пять вопросов:

1. Что было нужно построить?
2. Почему стандартное решение было недостаточно?
3. Какую систему создал ProAI Expert?
4. Какие реальные доказательства доступны?
5. Какой следующий шаг предлагается посетителю?

# 3. Narrative architecture system

## 3.1 Default case skeleton

Use as a starting point, not a rigid template:

1. **Claim / opening thesis** — one sentence defining what was built and why.
2. **Context / brief** — actual situation, constraints and audience.
3. **Risk / failure mode** — why a normal template or fragmented workflow was inadequate.
4. **Strategy** — decision logic and trust architecture.
5. **System** — what was built, by layers or connected roles.
6. **Experience walkthrough** — real interface and content evidence.
7. **Evidence** — verified facts, dated metrics, route/capability status.
8. **Perspective** — owner/client voice only when real and approved.
9. **Production** — responsive, SEO, accessibility, form, deployment.
10. **Result** — delivered system, not invented commercial outcomes.
11. **Next step** — one primary CTA and subordinate live/archive links.

## 3.2 Narrative rules

- Begin with a client/business problem, not a service list.
- Each chapter must introduce a new thought.
- Do not repeat “we built a system” in every section.
- Human/business meaning appears before engineering detail.
- Evidence follows the claim it supports.
- Technical proof appears late enough not to cool the opening.
- One strong case may be long; length is not a defect when orientation and rhythm are controlled.

## 3.3 Before → after framing

Use one controlled transformation frame when evidence permits.

Valid forms:

- fragmented information → coherent architecture;
- immediate booking pressure → context before calendar;
- generic template → individual identity;
- disconnected routes → bilingual mapped system;
- unstructured message → guided intake.

Invalid forms:

- fabricated old-site screenshots;
- fake revenue or conversion improvement;
- invented client quotes;
- implied “before” defects not verified in source material.

# 4. Premiumity system

## 4.1 Premiumity hierarchy

Prioritize in this order:

1. Content hierarchy.
2. Visual rhythm and whitespace.
3. Real evidence scale and legibility.
4. Typography and controlled line length.
5. Motion timing and sequence.
6. Decorative detail.

Never use decoration to compensate for weak structure.

## 4.2 Editorial rhythm

A premium long-form page needs:

- narrow copy columns;
- wider proof surfaces;
- long visual pauses;
- alternation between text-led, image-led and system-led chapters;
- fewer but larger visual moments;
- clearly different chapter densities;
- intentional transitions between dark and light fields.

Avoid repeating:

`heading → two paragraphs → screenshot card → facts grid`

for every chapter.

## 4.3 Screenshot breakout

Screenshots may extend wider than body copy when:

- the interface remains legible;
- the crop proves a specific point;
- safe page margins remain;
- mobile uses natural width and ratio;
- captions remain directly associated.

Do not use breakout for every image. Two to four major moments are normally enough.

## 4.4 Typography

- Display scale is project-specific.
- Body type remains highly readable.
- Serif is used when it fits the project world, not as a universal premium shortcut.
- Owner quotes can use a larger serif treatment when approved.
- Monospace is limited to status, routes, dates, evidence labels and technical annotations.
- All-caps labels remain short.
- RU and EN require separate line-break design.

# 5. Signature effect library

A case selects one signature family. Supporting effects are subordinate.

## 5.1 Grid Assembly

**Meaning:** precision, systems, designed structure.

Sequence:

1. local grid/rules appear;
2. primary module aligns into place;
3. evidence or screenshot resolves;
4. grid becomes quiet or static.

Use for:

- system-heavy cases;
- hero or architecture chapter;
- studio/process pages.

Do not:

- animate grid continuously;
- cover the entire page permanently;
- snap the user’s scroll;
- use on a human/editorial case unless extremely restrained.

## 5.2 Signal Path

**Meaning:** connected layers, journey or operational flow.

Sequence:

1. path is visible or resolves locally;
2. current node activates;
3. supporting content appears;
4. path rests.

Use for:

- five-layer architecture;
- consultation journey;
- intake flow;
- factory process.

Mobile:

- vertical static guide;
- no long animated line tied to scroll distance.

## 5.3 Editorial Threshold

**Meaning:** entering/leaving a project-specific world.

Forms:

- black → ivory;
- arch opening;
- color field crossing a chapter boundary;
- inverted closing arc into footer.

Use for:

- Alina Horb;
- cases with strong material/color identity;
- archive-to-case transitions.

Do not use as a generic curved section divider on every project.

## 5.4 Evidence Dossier

**Meaning:** verified, dated, source-aware proof.

Sequence:

1. exhibit/status label;
2. evidence surface;
3. source/date/limitation;
4. optional live link.

Use for:

- Search Console;
- route counts;
- capability status;
- production QA;
- live-system evidence.

Do not create a fake dashboard.

## 5.5 Portrait Presence

**Meaning:** authorship and human centre.

Sequence:

- portrait visible immediately or near-final;
- small scale/mask resolve;
- copy remains stable;
- no face-crossing clipping edge.

Use for personal brands and About chapters.

## 5.6 Scenario Sequence

**Meaning:** range of real problems or use contexts.

Use for local services:

- wall repair;
- door/trim;
- painting;
- punch-list;
- finished result;
- send-photos flow.

Motion:

- restrained image reveal;
- one active scenario at a time;
- no carousel as the only access method.

## 5.7 Language Pair Alignment

**Meaning:** localization parity, not translation decoration.

Desktop:

- matched frames side by side;
- first resolves, second follows after 100–140 ms.

Mobile:

- static stack in primary/secondary language order;
- visible labels;
- identical crop and viewport.

## 5.8 Layered Peel

**Meaning:** system layers being revealed.

Use sparingly for:

- 3–5 architecture layers;
- content/intake/automation stack.

Requirements:

- all layers remain understandable without motion;
- no 3D page turns;
- no excessive overlapping cards;
- mobile becomes normal vertical flow.

## 5.9 Screenshot Mask Reveal

Forms:

- vertical mask;
- horizontal mask;
- subtle crop expansion;
- restrained crossfade.

Recommended duration: 420–560 ms.

Avoid:

- heavy blur-to-sharp;
- strong perspective rotation;
- large parallax;
- repeated identical reveal on every screen.

## 5.10 Chapter Progress Rail

Desktop variants:

- slim left rail;
- slim right rail;
- top compact chapter index.

Mobile variants:

- current chapter label;
- short progress line;
- non-sticky in very short landscape viewports.

Use when:

- page has 8+ meaningful chapters;
- labels can remain concise;
- focus and anchors are accessible.

Do not use if it competes with project visuals.

## 5.11 Quote Field

Use only for real approved testimony.

Treatment:

- one large block;
- serif or project display face;
- generous whitespace;
- source name/role;
- no per-word animation.

## 5.12 CTA Handoff

Sequence:

1. closing thesis;
2. primary CTA;
3. subordinate live/archive link;
4. transition into canonical footer.

No working duplicate form unless the page’s actual purpose is intake.

## 5.13 Next-case Transition

Use on archive or after case completion only when it improves navigation.

Forms:

- project color enters locally;
- next screenshot and title resolve from opposite axes;
- no autoplay or forced navigation.

## 5.14 Local Material Transition

For local-service cases:

- warm-stone surface;
- forest/amber rule;
- subtle texture below legibility threshold;
- finished-result image as visual anchor.

Avoid faux wood, construction clichés or over-textured backgrounds.

# 6. Motion grammar

## 6.1 Default timing bands

| Motion type | Duration |
|---|---:|
| Button/arrow hover | 180–280 ms |
| Small label/rule | 280–420 ms |
| Screenshot/content reveal | 420–560 ms |
| Headline resolve | 560–700 ms |
| Hero/threshold composition | 760–920 ms |
| Major field transition | 640–900 ms |

## 6.2 Easing

Preferred expressive easing:

`cubic-bezier(0.16, 1, 0.3, 1)`

Use current canonical shell easing where inherited. Do not create many nearly identical custom curves.

## 6.3 Simultaneous motion limits

- maximum two prominent case effects at once;
- shell cube may continue independently;
- copy, screenshot, background and progress should not all animate together;
- stagger supports reading order, not spectacle.

## 6.4 Motion sequencing

Premium sequencing usually follows:

`structure → headline → primary visual → evidence/source`

not:

`everything fades up simultaneously`

## 6.5 Prohibited motion

- loader before content;
- scroll-jacking;
- mandatory snap scrolling;
- blanket fade-up on every paragraph;
- heavy WebGL dependency;
- pointer-following decoration;
- continuous floating cards;
- large screenshot parallax;
- blur-heavy mobile reveals;
- animated counters for weak metrics;
- sound;
- effects available only on hover.

# 7. Dark/light transition system

## 7.1 Transition types

### Type A — Surface handoff

A project-colored surface expands into the next chapter.

### Type B — Evidence mat

A light proof module enters a dark page without changing the whole background.

### Type C — Threshold edge

An arch, line or geometric edge mediates the color change.

### Type D — Chapter field

One full chapter changes field color for a clear narrative reason.

### Type E — Footer closure

Project environment resolves back into canonical black before footer content begins.

## 7.2 Rules

- transitions must correspond to narrative changes;
- avoid rapid black/white alternation;
- avoid full-page recoloring solely for novelty;
- preserve contrast and focus visibility;
- reduced motion uses final static boundaries;
- mobile may simplify geometry while keeping the color logic.

# 8. Evidence system

## 8.1 Evidence hierarchy

1. Real project/status.
2. Real production screenshot.
3. Architecture fact.
4. Dated metric snapshot.
5. Capability status.
6. Owner quote/testimonial.
7. External live link.

## 8.2 Evidence module anatomy

Every evidence item should identify as applicable:

- what is shown;
- route or system role;
- language;
- capture or review date;
- scope/window;
- source;
- limitation;
- live link.

## 8.3 Evidence presentation variants

- **Exhibit card:** one proof + source/date.
- **Paired proof:** UA/RU or before/system-after.
- **Evidence strip:** 3–5 verified facts.
- **Capability matrix:** live / implemented-human-review / tested-partial / planned.
- **System map:** connected architecture, not metrics.
- **Owner perspective:** real quote after proof.

## 8.4 Evidence rules

- never turn small metrics into fake success dashboards;
- no metric without date/window;
- no business interpretation without evidence;
- screenshots remain legible at rendered size;
- essential claims also appear as live text;
- source notes can be concise but not hidden;
- testimonials require approval;
- demo projects cannot use real-client phrasing.

# 9. Screenshot system

## 9.1 Capture before composition

Maintain two layers:

1. **Source capture inventory** — complete QA/reference set.
2. **Public visual assets** — selected/cropped/paired compositions.

Do not treat every source screenshot as a public asset.

## 9.2 Public screenshot rules

- focused crops over full-page miniatures;
- visible language/route labels;
- no fake devices by default;
- no perspective unless meaningfully justified;
- consistent paired viewport and scroll position;
- no personal data, tokens, console or errors;
- explicit dimensions and responsive sources;
- natural ratio on mobile;
- below-fold lazy loading.

## 9.3 Screenshot count

The public page should use enough images to prove the narrative, not to exhaust the route list.

Typical range:

- flagship system case: 8–12 public assets;
- editorial personal case: 8–12 assets including portraits;
- local-service concept case: 6–10 scenario/result assets;
- archive card: one primary preview, optional secondary crossfade only when useful.

# 10. CTA system

## 10.1 Hierarchy

- one primary action;
- one secondary live/project action;
- optional tertiary text link.

## 10.2 Responsive behavior

- mobile portrait: stacked inside bounded wrapper;
- mobile landscape: two balanced columns only when labels fit;
- tablet/desktop: one bounded row or project-specific left/right arrangement;
- equal practical height;
- secondary remains subordinate;
- external links use clear `↗` treatment;
- hover/focus motion remains subtle.

## 10.3 Copy

CTA should name the next step:

- Discuss a similar system.
- Discuss your project.
- View the live website.
- Send project context.

Avoid generic `Learn more`, pressure or scarcity.

# 11. Portfolio archive system

## 11.1 Current scale

With three primary cases, use editorial project stages, not filters.

Recommended order:

1. Financial Stream — real client system case.
2. Alina Horb — real personal-brand/editorial case.
3. Local Repair Pro — concept/factory showcase.
4. ProAI Expert — secondary internal studio case.

## 11.2 Card/stage anatomy

- project/client name;
- truth status;
- one-sentence claim;
- one primary screenshot;
- 1–2 verified facts or scope labels;
- categories;
- clear case link.

Cards may differ compositionally by project. They must share shell quality, not identical internal layouts.

## 11.3 Filters

Do not add filters until at least six materially different cases justify them.

## 11.4 Archive motion

Allowed:

- restrained color-field transition;
- screenshot resolve;
- title/label sequence;
- progress indicator;
- next-stage handoff.

Mobile uses normal flow, no sticky stacking dependency.

# 12. Homepage and service-page integration

## 12.1 Homepage

The homepage should become more concrete without becoming a condensed case study.

Include:

- clear service-business audience;
- one proof-backed flagship module;
- one concise explanation of human control and visible limits;
- direct routes to cases;
- founder/studio context;
- intake-first next step.

## 12.2 Service pages

Use a coherent structure:

1. Problem.
2. System/solution.
3. Process.
4. Proof from cases.
5. Boundaries and human oversight.
6. Next step.

Do not reduce services to capability lists or technology names.

## 12.3 Insights linkage

Insights should contextually link to relevant cases, and cases may link to supporting insights. Avoid generic sitewide link blocks.

# 13. Mobile strategy

## 13.1 Mobile is recomposed

Do not merely compress desktop.

Adjust:

- visual order;
- proof density;
- typography scale;
- chapter progress;
- CTA arrangement;
- screenshot crop;
- motion count;
- sticky behavior.

## 13.2 Mobile rules

- maximum one or two simultaneous animations;
- remove heavy filters/blur;
- no fixed CTA covering content;
- internal drawer scrolling;
- no horizontal galleries as sole access;
- full-width proof surfaces inside safe margins;
- touch targets at least 44 px practical size;
- 320 px remains complete;
- short landscape does not force 100vh compositions.

---

# 14. Accessibility and progressive enhancement

- WCAG 2.2 AA target.
- One H1 per route.
- Correct language and heading structure.
- Visible focus.
- Fixed header does not obscure targets.
- Chapter rail is keyboard-operable.
- Reduced motion stops non-essential motion.
- No-JS reveals all content.
- Screenshot controls are not fake form fields.
- Decorative geometry hidden from assistive technology.
- 200% zoom and 320 px reflow.
- No meaning depends on color, hover or animation alone.

---

# 15. Performance system

## 15.1 Perceived premiumity depends on speed

Required:

- one identified LCP candidate;
- responsive image sources;
- explicit dimensions/aspect ratios;
- lazy load below fold;
- transform/opacity motion;
- no layout thrash;
- limited route-specific JavaScript;
- no effect-only third-party library;
- font fallback without invisible content.

## 15.2 Mobile simplification

- replace blur with opacity/scale or desaturation;
- remove non-essential parallax;
- reduce active observers/listeners;
- avoid animated SVG paths across entire page;
- do not preload multiple screenshots.

## 15.3 Performance claims

Lab results are acceptance evidence, not public claims. Field Core Web Vitals require dated CrUX/Search Console evidence.

# 17. Anti-patterns

Reject:

- one universal visual style for every case;
- page-specific changes to canonical shell;
- motion before content hierarchy;
- every element animating;
- fake metrics or testimonials;
- unreadable long-page screenshots;
- equal visual weight for all CTA;
- dense card grids with little evidence;
- permanent technical grids;
- heavy blur and glow;
- excessive use of serif as a “premium” shortcut;
- three-dimensional device mockups by default;
- case pages that read like service pages;
- service pages that make claims without case proof;
- direct publication without owner visual review.
