# D. Final Visual Concept

## Concept name

# Integration Core — Controlled Assembly

This is the Hero-specific evolution of Concept A — Precision Grid.

## 1. Composition

Desktop remains broadly asymmetric two-column, but not a rigid 50/50 split.

Guideline at 1440:

- 44–47% information territory
- 53–56% signature visual territory

These percentages are design targets, **not hard laws**. Art direction and hierarchy win over arithmetic.

The object may push slightly toward the centre gutter, creating depth across the Hero, but no illuminated element crosses behind important copy or CTA controls.

The right side must **not** have a rectangular enclosing card.

## 2. Central object

A compact architectural monolith, approximately cuboid in overall volume but explicitly **not** the old six-faced word cube.

It is built from three visually distinct assemblies:

### Outer Presence Shell

Matte/anodized graphite planes.

Represents:

- positioning;
- website;
- proof;
- trust.

### Inner Intelligence Layer

A denser central body revealed through one or two narrow seams. Represents AI, logic and decision support. Cyan is emitted from inside, not painted over the whole object.

### Operations Spine

A rear/lateral structural rail that continues beyond the core toward response/follow-up. Represents automation and operational continuity.

The object should appear 85–90% assembled even in the strongest static frame. One offset layer and one illuminated inner seam provide complexity without chaos.

## 3. Geometry

Use:

- large clean planar surfaces;
- precise seams;
- asymmetric cuts;
- narrow visual gaps;
- one illuminated channel;
- slightly different layer depths;
- hard geometry softened only by realistic reflection.

Do not use:

- floating glass cards around it;
- orbit rings;
- spheres;
- particles;
- six large labels attached to cube faces;
- dozens of connector nodes.

## 4. Semantic surrounding system

One fine structured rail moves through the composition.

Conceptually:

`TRUST / PRESENCE → INQUIRY → CORE → RESPONSE → FOLLOW-UP`

All five words do not need equal prominence.

Default desktop frame should expose at most four concise semantic anchors. They are calibration labels attached to the rail/space, not UI cards.

AI and AUTOMATION should feel like internal mechanisms of the core, not two more orbiting boxes.

## 5. Depth

Depth is built through:

- overlapping graphite planes;
- perspective;
- controlled occlusion;
- material highlights;
- one deeper rear layer;
- negative space;
- tiny Z separation between modules.

No panel may visually pass through another panel. No label may look trapped inside the geometry.

## 6. Material

Primary material language:

- blackened graphite;
- anodized dark metal;
- near-black ceramic-like surfaces;
- a very limited smoked acrylic/glass insert only where the internal signal is visible.

No generic translucent glass-card language.

## 7. Lighting

Use three-light logic visually:

- soft neutral white key reflection from upper/front edge;
- extremely restrained deep-blue rear fill;
- cyan internal emission from the core seam/path.

Cyan should behave like information/signal, not general atmospheric decoration.

The brightest cyan UI object on the page should normally remain the primary CTA, not the 3D composition.

## 8. Background

Keep Concept A’s near-black graphite environment and precision grid, but localize the strongest grid visibility around the object.

Grid opacity should fade toward the copy.

One very soft ambient field behind the core is enough.

No moving background grid.  
No animated nebula.  
No giant blurred cyan blob.

## 9. Copy / visual relationship

The copy tells the business outcome.

The visual explains the system relationship.

They complement rather than repeat each other.

# F. Motion Choreography — FOR LATER CODE PROTOTYPE

**Important:** motion is defined here so the static art direction anticipates it, but the immediate next action is **NOT code**. First generate and approve the static 1440 composition.

## Initial state

Before any enhancement executes, the Hero is already visually complete.

The core is visible in a high-quality 3/4 composition with:

- outer plates nearly aligned;
- internal cyan seam visible;
- input/output rails visible;
- no dependency on animation for understanding.

## First 0–1 second

- two or three outer modules begin slightly out of alignment;
- they slide along controlled axes into the primary structure;
- the overall object changes angle only a few degrees;
- no bounce.

Meaning: fragmented → organised.

## Approximately 0.8–1.8 seconds

One cyan signal enters through the upstream rail.

The sequence becomes visible:

`Trust → Inquiry → Core → Response → Follow-up`

Not through five flashing labels, but through one moving signal, one seam becoming active and one downstream segment illuminating.

## Approximately 1.8–2.2 seconds

The assembly reaches final state.

One narrow neutral/specular reflection travels across one metal edge.

Then the Hero becomes quiet.

## Idle

- very slow yaw change, approximately ±1–2°;
- optional sub-degree pitch;
- 14–18 second cycle;
- cyan inner seam gently changes luminance rather than pulsing.

No 360° rotation.  
No constant orbit.  
No repeated signal running around the screen every few seconds.

## Pointer reaction — desktop only

- maximum approximately ±3° rotational influence;
- 3–5px relative depth between outer and inner modules;
- no cursor-following light ball;
- no labels chasing pointer;
- no perspective inversion.

## Scroll reaction

Do not implement continuous scroll parallax.

Use at most one mild threshold/state change when Hero starts leaving viewport, only if it improves the transition to the next section.

## Reduced motion

With `prefers-reduced-motion`:

- no assembly;
- no idle rotation;
- no pointer movement;
- no scroll response;
- no travelling highlight.

The final fully assembled static frame appears immediately.

# L. Implementation Feasibility — FOR LATER CODE PROTOTYPE

## Expert choice

# NO WebGL
# NO Three.js

The required visual does not need arbitrary camera movement, complex meshes, real-time environment mapping or a full 3D render loop.

Recommended future implementation model:

> **High-quality 2.5D DOM/CSS + inline SVG + minimal vanilla JS.**

Not a six-faced CSS cube.

Use:

- one perspective scene;
- 3–5 rigid layered planes/modules;
- CSS transforms;
- gradients/pseudo-elements for reflections;
- inline SVG for signal rails/path illumination;
- CSS opacity/transform animation;
- minimal JS for enhancement states, pointer variables and one scroll/intersection state.

Performance rules:

- transform/opacity only for continuous movement;
- no animated large blur;
- no animated backdrop-filter;
- avoid large SVG blur filters;
- no dozens of permanent `will-change` layers;
- no continuous JS animation loop when idle;
- pointer updates only while pointer activity exists;
- fixed visual aspect-ratio prevents CLS;
- core meaning exists in static DOM;
- no Hero raster/video dependency required.

Main implementation risk:

> A mediocre CSS object will look like a CSS experiment.

Therefore static silhouette/material/lighting must be approved **before motion is added**.
