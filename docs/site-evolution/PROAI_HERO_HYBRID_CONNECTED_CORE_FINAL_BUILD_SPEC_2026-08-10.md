# 1. Final creative decision

The Hero communicates one idea:

> **From first impression to follow-through — one connected system.**

The visual is not an AI mascot, reactor, dashboard, flowchart or decorative sci-fi object. It is a premium physical metaphor for a connected business system.

The hierarchy is:

1. editorial communication;
2. bespoke physical System Core;
3. four-stage business journey;
4. restrained material/light response;
5. motion only as clarification.

If an effect competes with that hierarchy, remove the effect.

# 4. Final desktop static composition

Target review frame: **1440 × 900**.

## 4.1 Global Hero frame

- one seamless near-black environment;
- no visible left/right panel boundary;
- shared production header system;
- content max width: approximately `1480px`;
- Hero content uses approximately `42% / 58%` editorial-to-scene allocation at 1440px;
- copy remains left-aligned and optically anchored to the production grid;
- 3D scene does not invade H1 reading space;
- background atmosphere is local and scene-driven, not a separate colored panel.

## 4.2 Core placement

At 1440 × 900:

- Core optical center sits near `72%` viewport X and `51%` Hero content Y;
- apparent Core width target: approximately `350–410px` depending on final camera calibration;
- Core is dominant on the right, but not larger than the communication hierarchy;
- Core receives a subtle grounding/contact response below it;
- silhouette must read clearly without cyan emission.

## 4.3 Final plate layout: stepped asymmetric progression

The R1 static layout uses **one stepped asymmetric progression**, not an orbit and not four equal corners.

Within the right scene coordinate space:

- `01 TRUST`: upper-left intake side, closest plate to the editorial copy boundary;
- `02 INQUIRY`: lower-left and slightly deeper toward the Core;
- `03 RESPONSE`: upper-right/output side, offset farther from the Core than 02;
- `04 FOLLOW-THROUGH`: lower-right stable terminal position.

The progression should read visually as left/intake → Core → right/output even with motion disabled.

No permanent connecting lines are used in R1.

## 4.4 Plate appearance

Each stage is a semantic DOM `button`/interactive plate with:

- strong `01–04` numeral;
- compact uppercase heading;
- one short microcopy line;
- wide editorial proportion;
- near-transparent graphite fill;
- one controlled border;
- no icons;
- no glowing glass-card treatment;
- no equal card dimensions requirement — small controlled differences are allowed for optical balance.

Inactive state remains readable at approximately 45–60% visual emphasis.  
Active state increases border/value contrast and a narrow cyan material cue; it does not become a neon card.

# 5. Final System Core geometry

## 5.1 Object definition

The Core is a **precision-machined contained instrument** derived from cube/Core lineage.

It uses the minimum geometry required for identity:

1. one rounded/chamfered outer graphite volume;
2. one dominant front intelligence aperture;
3. one contained internal cyan volume behind the aperture;
4. restrained structural rails around the aperture;
5. subtle directional asymmetry between intake and output sides.

Do not add rings, fins, random cuts, exposed machinery, circuit-board decoration, tubes, cables or repeated little windows.

## 5.2 Directional asymmetry

The left/intake side reads slightly more contained/closed.  
The right/output side reads slightly more resolved/open.

The asymmetry should be visible primarily through silhouette and edge structure, not through an explanatory arrow.

## 5.3 Aperture

One front-facing smoked-glass intelligence aperture is allowed.

Requirements:

- aperture occupies roughly 35–45% of the visible front face;
- shell thickness remains readable around it;
- internal cyan appears behind material depth, not painted on the surface;
- glass is dark/smoked and never becomes a transparent neon cube.

# 6. Material and light system

## 6.1 Primary shell

- graphite / gunmetal;
- high metalness;
- satin roughness, not chrome;
- restrained clearcoat only if it improves edge definition;
- bevel/chamfer highlights are the primary premium cue.

## 6.2 Aperture material

- smoked glass / restrained physical transmission;
- controlled Fresnel/specular response;
- no broad cyan glow around the whole object.

## 6.3 Internal intelligence

- one contained cyan emissive volume;
- cyan is deeper inside the object than the glass plane;
- stage states change internal intensity/position/coherence;
- no particle cloud is required.

## 6.4 Environment

Use a controlled studio reflection environment such as Three.js `RoomEnvironment`/PMREM for R1.

A custom HDRI may replace it later only if owner review shows a material-quality ceiling.

## 6.5 Warm reflection

A rare champagne/warm edge response may exist only as a physically plausible low-intensity environmental reflection from one light direction.

It is not a third accent color.

## 6.6 Bloom

No global bloom in R1.

If cyan appears luminous, it must come from emissive/material contrast and local light spill, not a visible post-process halo.

# 8. Signal / input → processing → output logic

R1 uses no permanent line or cable.

Narrative clarity hierarchy:

1. stage spatial positions;
2. directional Core geometry;
3. internal light-state movement;
4. active DOM plate emphasis.

Stage states:

### TRUST
Internal cyan is calm and contained, biased slightly toward the intake side.

### INQUIRY
The internal volume becomes more receptive/brighter and shifts toward the front/intake zone.

### RESPONSE
The light coheres and resolves toward the output-facing/right internal region.

### FOLLOW-THROUGH
The internal state becomes balanced and stable across the aperture, then settles.

A transient hairline trace is **not implemented in R1**. Add one only after owner review if the static/material narrative is genuinely unclear.

# 9. Motion state machine

R1 has one deterministic narrative authority.

States:

`BOOT → ESTABLISH → TRUST → INQUIRY → RESPONSE → FOLLOW_THROUGH → RESOLVE → IDLE → MANUAL_PREVIEW`

## 9.1 Timing

Target desktop sequence:

- `0.00–0.45s` BOOT: copy is already readable; Core begins from dark material definition, not scale explosion;
- `0.45–1.20s` ESTABLISH: plates settle into their static positions;
- `1.20–2.55s` TRUST;
- `2.55–3.95s` INQUIRY;
- `3.95–5.35s` RESPONSE;
- `5.35–6.95s` FOLLOW-THROUGH;
- `6.95–7.70s` RESOLVE;
- after `~7.7s`: calm IDLE.

No immediate full-story loop.

## 9.2 Manual preview

Hover, keyboard focus or tap on a stage:

- cancels pending autoplay;
- sets that stage active;
- moves Core internal material/light to the corresponding state;
- does not trigger a full object spin or camera move.

## 9.3 Idle

- no continuous full rotation;
- optional orientation drift under approximately `0.5°` over several seconds;
- internal light modulation remains below approximately 8–10% of the narrative intensity delta;
- pointer response, if available, is clamped to approximately `±2°` and applies only to the Core, not the plates.

# 10. Mobile recomposition

## 10.1 ~390px portrait

Reading order:

1. header;
2. eyebrow/H1/support;
3. CTAs + microcopy/accountability;
4. compact Core;
5. vertical 01–04 journey rows.

Rules:

- scene becomes a normal document-flow block;
- Core canvas target height: approximately `280–320px`;
- no floating desktop plates around the Core;
- stage rows are full-width, readable DOM blocks;
- no pointer/gyro interaction;
- DPR is reduced;
- glass/transmission and secondary light complexity may be reduced;
- one-time narrative may run faster, but reading never depends on animation.

## 10.2 ~320px portrait

- H1 remains readable without horizontal clipping;
- Core target height: approximately `240–270px`;
- preserve silhouette + one internal cyan identity only;
- stage rows remain full-width;
- secondary optical material subtleties that are not visible at this size are removed;
- primary CTA remains easy to tap.

## 10.3 Short landscape

For short landscape viewports:

- compact split layout: copy left / Core right where width allows;
- Core size is reduced;
- stages collapse into a compact strip/stack below the Core;
- no autoplay spectacle;
- support copy and CTA remain usable before decorative detail.

# 11. Reduced motion and fallback

## prefers-reduced-motion

- no autoplay narrative;
- no pointer response;
- no idle orientation drift;
- complete premium static composition is shown immediately;
- stage focus/tap can change active material state with near-instant or short opacity/value transitions only.

## WebGL unavailable / module failure

- show a CSS/DOM fallback Core silhouette in the same scene footprint;
- all copy, CTAs and stage information remain present and usable;
- failure of WebGL must never create a blank Hero.

---

# 12. Performance budget

R1 target budgets:

- one WebGL canvas;
- no post-processing chain;
- no remote HDR texture required for R1;
- approximately `< 25` meshes;
- approximately `< 25k` triangles;
- no runtime CSG;
- desktop DPR clamp approximately `1.65–1.75`;
- mobile DPR clamp approximately `1.15–1.25`;
- pause rendering when Hero is offscreen;
- pause rendering when document is hidden;
- no render work from pointer movement on touch devices;
- desktop target: stable 60fps-class behavior on current mainstream hardware;
- mobile target: graceful visual simplification before GPU-heavy detail.

Three.js is loaded only for the isolated prototype route. No global production dependency is introduced.

---

# 13. Accessibility gates

- H1 and all business meaning remain DOM text;
- stage elements are keyboard-focusable;
- visible focus ring is required;
- active stage is exposed with `aria-current` or equivalent state;
- canvas is decorative and `aria-hidden=true`;
- CTA contrast must remain readable;
- reduced-motion path is intentional;
- no hover-only information;
- WebGL failure preserves the complete narrative.

---

# 14. Static acceptance gate before motion approval

The prototype fails before motion review if any of the following are true:

1. Core reads as a default Three.js cube.
2. Core silhouette is weak with cyan intensity reduced.
3. Four stages read as four equal feature cards.
4. Layout reads as a symmetric orbit.
5. Copy and scene feel like separate panels.
6. Cyan becomes the object paint rather than internal intelligence.
7. Stage order is not understandable in a static frame.
8. Core appears to float without contact/grounding.
9. H1 loses visual authority to the object.
10. Mobile is merely a scaled desktop composition.

---

# 15. Motion acceptance gate

Motion fails if:

- the full story loops continuously;
- Core performs obvious repeated rotation;
- camera motion becomes a spectacle;
- plate typography moves enough to impair reading;
- pointer response exceeds restrained optical correction;
- animation is required to understand the stage order;
- reduced-motion looks like a broken/empty version;
- rendering continues unnecessarily offscreen/hidden.
