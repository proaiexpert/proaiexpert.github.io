## Product concept

### Controlled Execution Field / Authority Threshold

The field represents one operating AI system, not a collection of decorative cubes.

Narrative:

`REST → AI ACTIVATION → PROCESSING → ROUTING → RESOLUTION → AUTHORITY THRESHOLD → HUMAN CONTROL`

The single most important visual moment is:

> **INDIGO EXECUTION REACHES PEARL — AND STOPS.**

If Indigo automatically continues through Pearl, the concept fails.

## Semantic color roles

### Neutral / Silver

Meaning: machine work that is available, resolved, or inactive.

Base family:

- Obsidian `#020304`
- Black `#07090B`
- Graphite `#11151A`
- Gunmetal `#1A2027`
- Silver `#C9CDD1`

### Indigo

Meaning: **AI is working here now.**

Primary:

- Indigo `#676BFF`
- Indigo Soft `#A8B0FF`

Indigo is a transient execution state, not a permanent decorative accent.

### Pearl

Meaning: **automatic authority ends here.**

Primary:

- Pearl `#F2F0EB`

Pearl is not an AI-active state.

**Pearl must never become Indigo.**

## Owner-review finding after capability proof

The selective-state mechanism is technically accepted, but the current capability preview is **not visually accepted as a product state** because the Owner could not perceive a meaningful color/state difference on iPhone.

Therefore the next implementation must not merely prove that two individual cubes changed material values. It must make the semantic sequence perceptible in the actual Hero composition while preserving premium restraint.

This does **not** authorize neon, broad color flooding, or global Indigo.

## Path architecture

The first production-oriented choreography should use a **small coherent chain**, not isolated random cubes.

Target structure:

1. **AI AGENT** — initial Indigo activation
2. **AUTOMATION** — receives Indigo
3. **API** — receives Indigo
4. **CUSTOM CODE** — receives Indigo
5. **DECISION GATE** — Pearl, never Indigo

The exact instance IDs may differ from the three-instance capability proof if a better spatial chain exists in the frozen Hero composition.

Selection priority:

1. right-side visibility;
2. coherent adjacency / readable route;
3. strong native hover visibility;
4. no copy collision;
5. no camera/framing changes required.

## Intro timing target

Target total intro: approximately **3.8 seconds**.

### 0.00–0.32 — REST

- Neutral field.
- No global motion wave.
- No Indigo yet.
- Pearl already exists as Pearl if visible in the chosen path.

### 0.32–0.82 — AI AGENT activation

- One upstream module becomes Indigo.
- Activation should feel like the system coming online, not a neon flash.

### 0.72–1.20 — Agent → Automation

- Indigo execution advances to the next module.
- Previous module may remain softly active or begin resolving, depending on what reads best.

### 1.14–1.62 — Automation → API

- Route continues.
- No broad field-wide pulse.

### 1.56–2.04 — API → Custom Code

- Indigo reaches custom-code stage.
- Color remains controlled and local.

### 1.98–2.48 — Local routing

- A small amount of local neighboring activity may acknowledge routing.
- Maximum restraint: no expanding ripple across all 143 cubes.

### 2.42–3.08 — Reach Pearl

- Indigo reaches the machine-side module immediately before Pearl.
- Pearl may acknowledge slightly through luminance/physical response.
- **Pearl stays Pearl.**
- Indigo terminates before Pearl.

### 3.08–3.48 — Resolution

- Upstream machine modules resolve toward Silver/neutral.
- The route visibly calms.

### 3.48–3.80 — Hold

- Calm final state.
- No endless looping wave.
- The final Hero should look intentionally composed even when motion has stopped.

## Final calm state

The final state after intro should solve the earlier weak-native-rest problem through **semantic composition**, not by globally brightening the entire donor.

Preferred calm read:

- majority neutral / dark field;
- a small resolved Silver path remains legible;
- at most one upstream module may retain a restrained Indigo acknowledgment if required;
- Pearl Decision Gate remains clearly visible and distinct;
- no permanent Indigo flood;
- no animated loop required.

## Motion principles

Motion must feel:

- deliberate;
- engineered;
- low-amplitude;
- spatially causal;
- premium;
- readable once, then calm.

Forbidden:

- continuous cyberpunk waves;
- random blinking;
- RGB cycling;
- global pulse;
- particle fireworks;
- camera swoops;
- springy cartoon bounce;
- persistent looping execution.

## Native hover

Native Boxes Hover interaction must remain intact.

The semantic intro is layered onto the existing donor behavior; it does not replace hover.

Required:

- 143 Cube meshes preserved;
- 143 material identities preserved unless an implementation-specific reason is documented;
- native center hover remains dimensional;
- native edge hover remains coherent;
- pointer leave settling remains native;
- semantic modules must not become frozen/detached cubes.

## Implementation mechanism preference

Preferred order:

1. native serialized states / events / instance overrides;
2. serialized state variants addressed to exact target instances;
3. runtime triggering of **pre-authored native scene states/events** only if necessary;
4. avoid direct post-load material mutation.

Forbidden by default:

- `setMaterial()`;
- `createCustomMaterial()`;
- Three.js reconstruction;
- manual `BoxGeometry`;
- broad live material mutation;
- CSS glow used as a fake 3D semantic state.

## Material rule

Base material remains accepted R3.

Do not reopen global material exploration during choreography implementation.

Only semantic target-state values may vary, and only where required for Indigo / Pearl / resolved Silver.

No Champagne/Violet exploration in this phase.

## Label strategy

Labels are **not required in the first choreography implementation**.

Phase 1 goal:

> Can the physical field itself communicate execution and stop authority clearly enough?

If the motion/state choreography passes without labels, keep the Hero cleaner.

If labels become necessary later, use at most the five frozen semantic anchors and keep them subordinate to the physical field.
