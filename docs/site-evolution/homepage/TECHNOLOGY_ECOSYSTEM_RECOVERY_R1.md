## Important recovered decisions

The Transition R2 owner study explicitly compared:

- marks only;
- hybrid wordmarks;
- mark + label.

It selected **mark + label** for recognition consistency and optical normalization.

It also tested 10, 12 and 14 identities. Ten was retained because 12/14 moved toward logo-wall density.

Its art-direction study considered Conductive Seam, Optical Scan and Structural Assembly. The implemented recommendation was effectively **Conductive Seam + Structural Assembly discipline**. Continuous marquee, generic cards, particles and dashboard/network metaphors were rejected.

The older Workflow Environment commit confirms why marquee-era treatment was left behind: it required visibility/tap-glow corrections yet still presented tools primarily as a moving set rather than as system architecture.

## Capability / information-integrity audit

The current repository directly supports conservative claims about AI systems, workflow automation, integrations and delivery. Financial Stream provides concrete evidence of:

- Gmail + Make + OpenAI drafts: implemented with human review;
- Twilio / Make components: tested / partial;
- GitHub: active delivery/source-control environment.

The repository also carries Claude, Gemini, n8n, Zapier and Vercel in the Technology candidate/selected platform set, but current production evidence does not justify implying that every displayed vendor is a formal partner or a regularly deployed tool in every project.

Public wording therefore treats the marks as **technology capability / available platform choices**, explicitly states that the stack varies by system, and avoids partner/certification language.

All 10 current mark assets were reverified on `main` under `assets/brand/platforms/`.

## Three new directions considered

### A — System Instrument

Recover the R1 calibration logic as a contemporary control surface: operating requirements converge on SYSTEM FIT, then expose technology roles.

Strength: maximum explanatory clarity.  
Risk: can become a fake dashboard or overly literal “control panel”.

### B — Material Architecture

Recover R4/R5 physicality as one premium object with four technology territories.

Strength: strongest tactile/material impression.  
Risk: visually repeats the Hero cube/object language and reintroduces WebGL/3D burden.

### C — Resolved System Field — SELECTED

A full-width material architecture field:

`OPERATING REQUIREMENTS → SYSTEM FIT → TECHNOLOGY ROLES → SELECTED TOOLS`

Four role lanes are always legible. Selecting a role makes that lane authoritative and brings its actual platform marks forward. The field uses SVG/CSS/semantic HTML rather than WebGL.

Why selected:

- retains R1 clarity;
- retains R4 “valid configuration” logic without geometry solver complexity;
- retains R5 meaningful family inspection without another cube;
- retains Relay one-shot choreography and settled rest;
- works as a desktop chapter and can deliberately recompose on mobile;
- keeps all essential information in real HTML;
- has materially lower performance and maintenance risk.

## Implementation rationale

The flagship is implemented as semantic HTML + scoped CSS + restrained vanilla JS + decorative SVG.

Motion architecture:

1. section becomes materially visible;
2. requirements establish;
3. central SYSTEM FIT resolves;
4. four role lanes draw;
5. technology identities settle;
6. hover/focus/tap can inspect a role;
7. no perpetual motion remains.

The component uses no continuous render loop, no Canvas/WebGL, no runtime-generated textures and no external visual dependency beyond the existing repo brand assets.

Accessibility:

- real heading and copy remain in HTML;
- all technology names remain real text;
- four role controls are native buttons;
- keyboard focus reveals equivalent state;
- click/tap locks and unlocks role state;
- Escape returns to REST;
- `aria-pressed` communicates locked role state;
- decorative architecture is hidden from assistive technology;
- `prefers-reduced-motion` collapses choreography to the stable state.
