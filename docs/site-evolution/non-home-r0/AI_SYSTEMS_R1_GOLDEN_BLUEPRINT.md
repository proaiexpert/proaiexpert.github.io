## 2. Locked concept

# THE OPERATIONAL REGISTER — SIGNAL → CONTROL

Core sequence:

`CAPTURE → CONTEXT → ROUTE → [ HUMAN CHECK ] → ACTION`

Critical rule:

> **HUMAN CHECK IS A CONTROL GATE, NOT A PEER PROCESS STEP.**

The page is not about “adding AI.” It is about creating a controlled operating layer between incoming information and the next permitted business action, using AI only where contextual interpretation creates real value and where risk boundaries are understood.

The transformation is:

**fragmented operational signal → registered context → controlled route → explicit human authority boundary → permitted action**

Do not reinterpret the sequence as five equal columns, five cards, a horizontal rail, a process diagram, or a SaaS workflow screen.

## 9. Chapter 03 — THE OPERATIONAL REGISTER / Signature revelation

This is the signature section and the most important visual system on the page.

### Physical model

**Precision registration bed / operational ledger.**

It should feel closer to an engineered registration surface, technical ledger, or precision control document than to software UI.

### Geometry

- one wide planar object;
- square or minimally softened corners (`0–8px` preferred);
- thin horizontal base rules;
- precise vertical registration marks;
- five semantic zones suggested by spacing, labels, rules, and state — not five boxed columns;
- 7–10 information strips of different lengths;
- disciplined microtype and significant negative space;
- no browser chrome, tabs, fake nav, charts, widgets, or software controls.

### Meaning of stages

**CAPTURE** — What arrived?  
**CONTEXT** — What do we already know / what is missing?  
**ROUTE** — Where does it belong / who owns it?  
**HUMAN CHECK** — Is autonomous action permitted, or is review/escalation required?  
**ACTION** — What is actually allowed to happen next?

### Human Check distinction

Machine/state signal = controlled Indigo.  
Human authority / truth / permission = Pearl/Silver.

A stronger Pearl/Silver boundary must interrupt the machine path before ACTION. Indigo must not visually flow uninterrupted through HUMAN CHECK.

The gate may be expressed through a strong rule, gap, bracket, interruption, or threshold — but not as another boxed step or tab.

### Signature choreography

One meaningful registration event, played once and then permanently settled.

Recommended total: roughly `950–1050ms`.

Suggested sequence:

- `0–180ms`: raw fragments become optically stable;
- `160–620ms`: fragments register to common baselines/reference rules;
- `500–760ms`: CAPTURE / CONTEXT / ROUTE stage marks resolve;
- machine signal approaches the Human Check boundary and stops;
- `690–860ms`: Pearl/Silver Human Check authority resolves;
- `820–1000ms`: ACTION becomes permitted / readable;
- final state becomes calm and still.

No replay loop. No idle pulse. No repeated full choreography on scroll-back.

### Reduced motion

Render the final registered semantic state immediately. Optional opacity/state feedback only, approximately ≤150ms.

### No-JS state

Core content and the final semantic model must remain visible if JS fails.

**Business question:** How does ProAI decide whether AI is appropriate at all?

> **Мы начинаем не с AI, а с процесса.**

#### FIX THE PROCESS
Use when ownership, sequence, rules, or responsibility are unclear.

#### AUTOMATE THE RULE

#### USE AI

## 25. Technical implementation direction

The signature concept does **not** inherently require WebGL, Three.js, or a heavy animation runtime.

Preferred implementation hierarchy:

- semantic HTML;
- CSS Grid / modern layout primitives;
- CSS custom properties;
- `transform` / `opacity` for motion;
- `IntersectionObserver` for one-time semantic triggers;
- Web Animations API or CSS transitions where sufficient;
- `prefers-reduced-motion`;
- progressive enhancement;
- final registered state visible if JS fails.

A library may be justified later only if it materially reduces risk/complexity while respecting budgets. Do not introduce one for prestige.

Performance targets remain targets until measured:

- initial JS ≤80KB gzip, preferred <50KB where practical;
- no unnecessary third-party visual runtime;
- no autoplay Hero video;
- above-fold compressed media ≤350KB target;
- mobile initial route ≤900KB target;
- LCP ≤2.5s p75 target;
- CLS <0.10;
- INP <200ms.

Do not report target values as measured passes.
