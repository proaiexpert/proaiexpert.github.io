# Website Production Factory Blueprint

## Mission

Create repeatable, premium websites across niches:

- handyman and local services;
- construction;
- accounting and bookkeeping;
- dental and medical clinics;
- expert-led personal brands;
- professional services.

The factory produces complete website systems, not one-off pages. Reuse applies to production discipline, patterns, QA, and workflow. It does not permit reuse of client facts or a single visual style across unrelated projects.

## Canonical premium standard

Read `PREMIUM_SITE_EXPERIENCE_STANDARD.md` before visual direction or implementation.

It defines the reusable standard for:

- trust-problem definition;
- strategy before surface;

## Operating Pipeline

1. **Intake**
   - Collect business facts, geography, service scope, proof, contacts, language needs, form destination, and constraints.
   - Separate verified facts, owner-provided facts, assumptions, unavailable proof, and prohibited claims.

2. **Niche / Competitor Research**
   - Identify competitors, offers, local search patterns, service language, trust signals, user expectations, and compliance constraints.
   - Identify generic visual patterns to avoid and meaningful category conventions to preserve.

3. **Trust Problem Definition**
   - Define the primary uncertainty that prevents the next step.
   - Select the primary trust type: operational, personal, practical service, clinical/regulated, local-market, or technical/system.
   - Define what the website must make clearer before contact.

4. **Sitemap and Information Architecture**
   - Define homepage, services, service-area hub, city pages, pricing approach, guides, about, request/contact, FAQ, and any regulated or language-specific routes.
   - Define canonical content ownership and prevent unnecessary duplication.

5. **Conversion Strategy**
   - Define primary CTA, secondary CTA, request flow, trust architecture, proof limits, and mobile conversion path.
   - Define the first meaningful action before deciding whether a calendar, message, form, or phone action belongs first.

6. **Copy Strategy**
   - Write conversion-focused, proof-safe copy.
   - Avoid fake reviews, ratings, licenses, warranties, insurance claims, customer outcomes, guaranteed results, and unsupported performance language.
   - Distinguish live, implemented, tested, partial, planned, concept, and in-development states.

7. **Signature System**
   - Define one project-specific functional system that makes the offer, decision path, proof, or customer journey clearer.
   - Examples include structured intake, bilingual alignment, service selection, evidence register, photo guidance, editorial threshold, or responsive reflow.
   - Do not invent a decorative signature without functional value.

8. **Evidence and Screenshot Plan**
   - Define Hero proof, signature proof, operational proof, responsive proof, and closing proof.
   - Prefer deeper system evidence over repeated homepage screenshots.
   - Document source, date, status, limitations, and reuse rules.

9. **Visual Direction**
   - Define audience, local or professional tone, imagery style, color system, typography, spacing, surfaces, screenshot treatment, and CTA hierarchy.
   - Hero should show the premium outcome, identity, or useful proof—not defects or fear unless the strategy explicitly requires it.
   - Create a surface map and editorial rhythm before styling every section.

10. **Motion Direction**
    - Define one restrained motion family tied to hierarchy or state.
    - Provide complete reduced-motion and no-JS behavior.
    - Exclude scroll-jacking, continuous parallax, particles, cursor trails, autoplay narrative, and blur-dependent content.

11. **Responsive Recomposition**
    - Define content order for desktop, tablet, mobile, and narrow mobile.
    - Specify H1, proof, CTA, navigation, captions, and elements that must never be removed.
    - Treat mobile as a deliberate composition, not a smaller desktop layout.

12. **Homepage Prototype**
    - Build the first complete screen and core conversion sections.
    - Use scenario images when real project proof does not exist, with truthful labeling.
    - Validate static hierarchy before adding motion.

13. **QA**
    - Run source QA, rendered desktop QA, rendered mobile QA, accessibility QA, link QA, content-safety QA, bilingual QA, performance QA, and live/cache QA.
    - Use the full factory checklists rather than source inspection alone.

14. **Deployment**
    - Verify source HEAD, origin/main HEAD, deployment source, live HTML/CSS/JS, indexing state, cache-busted URLs, forms, metadata, and redirects.

15. **Launch Readiness**
    - Confirm claims, service areas, CTA path, forms, mobile behavior, canonical/hreflang where relevant, performance budget, accessibility, and final owner approval.

16. **Reusable Template and Experience Extraction**
    - Extract niche-specific patterns, prompts, page structures, risks, image rules, signature-system lessons, motion lessons, responsive lessons, proof patterns, and failed experiments into factory docs.
    - Do not copy client-specific facts or visual identity into another project.

## Reuse vs Client-Specific Boundaries

Reuse:

- structure logic;
- QA process;
- mobile and responsive rules;
- local-service CRO patterns;
- intake-first strategy;
- trust-problem framework;
- evidence classes;
- accessibility baseline;
- performance rules;
- deployment QA;
- Codex workflow;
- task and prompt patterns;
- post-launch extraction method.

Adapt rather than copy:

- signature-system type;
- chapter rhythm;
- screenshot hierarchy;
- motion family;
- surface planning;
- CTA logic;
- multilingual architecture.

Never reuse without current-client verification:

- business name;
- service area;
- phone and email;
- real photos;
- reviews;
- testimonials;
- licenses;
- insurance;
- certifications;
- guarantees;
- warranties;
- pricing;
- availability;
- customer outcomes;
- metrics;
- before/after examples;
- language scope;
- deployment target;
- operating status.

## Strategic Lessons

- A website is a productized system, not a one-off page.
- Premium quality is production discipline, not one visual style.
- Every project needs a defined trust problem.
- Every premium project should have one functional signature system.
- Proof hierarchy must be planned before screenshot placement.
- A demo proves structure; it must not fabricate customer proof.
- Mobile requires recomposition, not reduction.
- Multilingual scope requires route and metadata architecture, not browser translation.
- Motion must reveal hierarchy and remain optional.
- Every launch should improve the factory through documented extraction.
- Local-service websites need clear services, service area, pricing approach, request flow, trust structure, FAQ, and mobile CTA.
